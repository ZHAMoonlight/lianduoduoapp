# 练多多四端技术设计

首版使用 TypeScript、React 和 Vinext 构建响应式界面，运行于 Cloudflare Worker，业务数据持久化到 Cloudflare D1。一个登录拥有者对应一个独立业务体验空间，空间内的五个固定身份用于验证四端流程。这个存储与身份设计适合产品体验和业务规则验证，真实品牌协作需要扩展组织成员及逐笔账务记录。

## 模块边界

| 模块 | 职责 |
| --- | --- |
| 页面与工作台 | 展示角色范围内的数据，收集操作参数，提交当前空间版本，展示服务端错误 |
| `app/app/api/workspace/route.ts` | `GET /api/workspace?persona=...`，返回该身份的数据投影与版本 |
| `app/app/api/actions/route.ts` | `POST /api/actions`，处理有权限的业务动作 |
| `app/lib/domain.ts` | 授权、状态转换、预约检查、课时变化、结算记录与操作记录 |
| `app/lib/workspace-store.ts` | 从 D1 读取拥有者数据，使用版本号执行乐观并发控制 |
| `app/lib/request-auth.ts` | 从可信认证头取得拥有者或限制到本机演示身份 |
| `app/lib/seed.ts` | 为新拥有者创建品牌、门店、教练、学员、课时卡、课程和履约示例 |

服务端领域逻辑是规则入口。界面禁用按钮只用于改善体验，不能替代服务端的角色、品牌和门店检查。

## 数据与身份

托管环境使用 `oai-authenticated-user-id` 作为稳定拥有者键。用户名称和邮箱用于显示，不能作为记录所有权的主键。未登录的线上请求应返回未授权；开发演示身份只能在明确的本机开发条件下启用。

生产入口必须由可信托管代理写入身份头，并清除访问者提交的同名头。直接暴露 Worker 时应配置独立身份校验，不能信任互联网上任意请求声明的拥有者 ID。

空间表 `workspaces` 保存 `owner` 主键、`data` JSON 业务数据、`version` 单调递增版本和 `updated_at` 更新时间。所有查询和更新都按服务端确定的拥有者键定位记录，客户端不能选择其他拥有者。首个空间版本为 1；并发初始化通过主键冲突忽略后重新读取处理。

```text
workspace owner
  ├─ tenants
  │    └─ stores
  │         ├─ coaches
  │         ├─ members
  │         └─ classes
  ├─ cards → member + selling store
  ├─ bookings → class + member + card
  ├─ settlements → completed booking + two stores
  ├─ tasks and announcements
  └─ audit events
```

各业务对象仍保留品牌 ID 和门店 ID。拥有者隔离解决不同登录者的体验数据隔离；品牌和角色过滤解决同一空间内的业务可见范围。这是两个独立检查，不能互相替代。

## 动作处理

客户端提交 `persona`、`action`、`payload` 和读取数据时取得的 `version`。服务端从固定身份列表解析身份，不接收自定义角色或权限。

写入接口只接受 `application/json`，请求体上限为 64,000 个字符，并预检查声明的内容长度。请求带有 `Origin` 时必须与当前请求地址同源；无 `Origin` 的可信服务端调用仍需有效拥有者身份和业务权限。

每个动作依次执行身份识别、空间读取、版本检查、字段校验、对象及权限校验、领域规则、数据转换和条件更新。预约、冻结、消费、结算及对应操作记录在一次空间更新中提交，避免只保存其中一部分。

```sql
UPDATE workspaces
SET data = ?, version = version + 1, updated_at = ?
WHERE owner = ? AND version = ?;
```

更新影响一行才表示成功。影响零行说明其他请求已修改空间，应返回 `409`，客户端刷新最新数据后再由用户重试。不得用旧 JSON 无条件覆盖整个空间，也不能先展示成功再忽略持久化失败。

全空间版本同时保护场次容量、学员重复预约和卡片冻结。例如两个请求同时争用最后一个名额，只有一个版本提交可以成功，另一个必须重新读取后判断是否还可预约。

## 状态和数据不变量

| 领域 | 必须保持的不变量 |
| --- | --- |
| 课时卡 | 总课时不为负，`0 ≤ frozen ≤ remaining ≤ total`，可约课时为 `remaining − frozen` |
| 预约 | 同一学员同一场次只存在一个未取消预约；有效预约不能超出容量 |
| 履约 | `reserved → checked_in → completed`；普通取消只允许从 `reserved` 进入 `cancelled` |
| 课时转换 | 创建增加冻结；取消释放冻结；完成同时减少剩余和冻结 |
| 排课 | 起止时间有效，容量和课时为正整数；教练和教室没有有效课程重叠 |
| 跨店单据 | 每个完成预约至多一条；来源是售卡门店，去向是履约门店；确认不表示实际付款 |
| 权限 | 课程、教练、卡片、学员和门店必须属于同一品牌，且在操作者范围内 |
| 审计 | 只有提交成功的动作追加记录；重复状态请求不会追加重复消费或结算 |

幂等状态转换和请求幂等需要区分。对已完成预约再次请求完成，应返回同一结果；用户以旧版本重试仍可能先收到版本冲突。创建租户、课程、任务等动作若需要网络断开后安全重试，生产版应增加请求幂等键。

## 时间和金额

事件时间使用 ISO 8601 时间戳，业务界面按 Asia/Shanghai 展示。`datetime-local` 表单输入按上海时间解释。日期类有效期包含上海时间到期当天，预约及资质检查使用上课日期。取消必须严格早于开课前 60 分钟；签到窗口为开课前 2 小时至结束后 2 小时；消课必须已经开课。

金额以整数分计算，课时以整数节计算。课程 `price` 是单场展示价格，卡片 `unitValueCents` 是单节内部结算价值，二者不能混用。跨店单据 `amount` 等于卡片单节结算价值乘以本次消耗课时。生产规则还应保存实付分配、加盟分配比例和舍入方式快照；结算产生后不随商品价格修改。

## 接口约定

| 结果 | HTTP 含义 | 客户端处理 |
| --- | --- | --- |
| 成功读取或提交 | `200` | 使用返回的数据与最新版本重新渲染 |
| 未登录 | `401` | 引导通过托管登录入口登录 |
| 越权或对象不在范围 | `403` 或不暴露对象的 `404` | 保持当前数据，显示不可操作原因 |
| 参数或业务条件不满足 | `400` 或 `422` | 展示字段或业务错误，不改变课时 |
| 空间版本冲突 | `409` | 刷新数据，明确告知数据已更新 |
| 数据库或服务不可用 | `5xx` | 显示保存失败，保留表单，禁止伪成功 |

具体动作名和字段定义以 `app/lib/types.ts` 为准。外部支付、通知、实名和文件上传没有适配器时，界面应展示接入状态，不返回虚构的外部服务成功结果。

## 当前存储限制

操作记录只保留空间内最近 500 条，用于体验操作追踪，不能作为完整财务审计档案。示例课时卡有期初余额，界面可见预约不是全部历史售卡和消费流水，因此不能从示例预约反推出卡的完整账龄。

教练、卡片、课程等记录没有删除和任意修改入口。证书补传、已审核结果复核、停课与冲正需要独立动作；不能通过直接改 JSON 绕过规则后继续真实经营。

## 生产化演进

单行 JSON 的代价是所有空间操作竞争同一个版本，更新时读写整个空间，无法对明细建立独立数据库约束和高效分页。生产品牌多人协作应迁移为租户、成员授权、场次、预约、课时流水、订单、结算和审计独立表，并保留 `tenant_id` 约束及相应索引。

课时变动应扩展为追加式权益流水，退款和消课纠错通过冲正处理。支付回调需验签、校验商户及金额，按外部交易号和业务订单号去重。通知通过独立待发记录执行重试，避免外部调用失败回滚已经确认的业务消费。

真实证书及课堂资料进入对象存储后，应使用短时授权访问、资料用途限制与可追踪的删除流程。备份恢复、数据导出、角色授权变更及大批量数据需要在真实门店试点前单独验证。
