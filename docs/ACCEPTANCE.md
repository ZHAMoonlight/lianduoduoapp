# 练多多四端验收标准

验收以服务端保存的业务结果为准。页面提示成功后，刷新页面仍应保留相同数据；界面隐藏按钮不能替代接口权限校验。首版验收范围是私有体验空间及四端核心流程，微信、支付和实际资金结算按产品设计中的接入边界验收展示文案。

## 验收准备

使用新的登录拥有者创建初始体验空间，记录初始空间版本、可用课时和已存在预约。准备一个未来可约场次、一个已到履约时段的场次、一张品牌通用卡，以及不同门店的售卡和履约组合。数据初始化时间应随首次创建空间生成，避免未来日期变成过期场次。

接口用例应直接提交请求验证，不能只点击可见按钮。每次成功动作均使用服务端返回的最新版本。为验证并发，先读取同一版本，再从两个请求分别发起动作。

## 核心业务用例

| 编号 | 操作 | 预期结果 |
| --- | --- | --- |
| B01 | 学员用适用卡预约未来课程 | 新预约为 `reserved`，冻结增加对应课时，剩余不变，可约减少 |
| B02 | 预约后刷新 | 预约及课时状态保持；四端显示相同履约事实 |
| B03 | 对同一场次重复预约 | 不产生第二条有效预约，不重复冻结 |
| B04 | 用余额不足、被冻结或到期的卡预约 | 请求失败，卡和场次人数均不改变 |
| B05 | 用其他学员或其他品牌的卡预约 | 请求被拒绝，不泄露无权访问的对象详情 |
| B06 | 用仅本店卡预约另一门店，或约不适用课程类型 | 请求失败，冻结不变 |
| B07 | 卡当前有效但在上课前过期 | 请求失败 |
| B08 | 最后一个名额被两个同版本请求争用 | 最多一笔成功；另一笔版本冲突或刷新后提示已满 |
| B09 | 同一学员预约时间重叠的两场课 | 后一预约被拒绝；首场结束时开始的课程不视为重叠 |
| B10 | 截止前取消预约 | 状态为 `cancelled`，冻结释放，剩余不变，名额可再预约 |
| B11 | 到达开课前 60 分钟或更晚再取消 | 学员自助取消失败，预约与课时不改变 |
| B12 | 取消成功后再次提交取消 | 不再次释放课时；旧版本可先返回版本冲突 |
| B13 | 店长或授课教练为到时预约签到 | 状态变为 `checked_in`，仍保持冻结，不重复扣课 |
| B14 | 完成已签到预约 | 状态为 `completed`，剩余与冻结均减少一次，并出现履约记录 |
| B15 | 对完成预约重复提交消课 | 不重复扣课，不生成第二条结算单 |
| B16 | 未签到直接消课，或取消后消课 | 请求失败，课时不改变 |
| B17 | 同店完成预约 | 不生成跨店结算单 |
| B18 | 品牌通用卡跨店完成预约 | 产生一条售卡门店到履约门店的待确认单，金额符合本版明确的计算规则 |
| B19 | 总部确认跨店单，再次重复确认 | 首次变为 `confirmed`，重复确认不改变金额，不声称已实际转账 |

## 门店与协同用例

| 编号 | 操作 | 预期结果 |
| --- | --- | --- |
| M01 | 店长邀请教练并审核通过 | 教练由待审核进入可排课状态；审核记录可追溯 |
| M02 | 为未审核通过的教练排课 | 请求失败 |
| M03 | 排课时结束早于开始、容量为零或课时非正整数 | 参数校验失败，不产生场次 |
| M04 | 给同一教练或同店同教室创建重叠课程 | 请求失败；紧邻起止时刻允许 |
| M05 | 总部为指定门店下发任务 | 本店店长能看到任务，其他品牌身份不能看到 |
| M06 | 店长完成本店任务并刷新 | 总部和门店都显示已完成，完成时间保持 |
| M07 | 平台维护租户资料或审核入驻申请 | 状态持久化；品牌资料审核不展示商户号已开通 |
| M08 | 平台或总部发布公告 | 按组织和受众展示，员工公告不向学员暴露 |
| M09 | 证书在课程开始日期前过期，尝试排课或预约 | 两个入口均拒绝；到期当日仍有效 |
| M10 | 在本店排课时替换成其他门店教练 ID | 请求拒绝，不创建无法履约的跨店课程 |
| M11 | 用不存在的公历日期创建课程 | 请求失败，不把错误日期自动归一化为下个月 |

## 权限与隔离用例

| 编号 | 操作 | 预期结果 |
| --- | --- | --- |
| S01 | 线上匿名读取或修改空间 | 返回 `401`，不自动取得共享开发身份 |
| S02 | 两个登录拥有者分别修改同一示例品牌 | 各自空间独立，互不可见，刷新不串数据 |
| S03 | 提交不存在的 persona 或自定义权限字段 | 请求拒绝；角色范围只来自服务端固定定义 |
| S04 | 店长提交其他门店的排课、教练或履约对象 | 请求拒绝；不能通过替换 ID 越权 |
| S05 | 教练提交另一位教练的预约签到或消课 | 请求拒绝 |
| S06 | 学员提交本人与绑定孩子以外的 memberId | 请求拒绝 |
| S07 | 店长、教练或学员尝试确认结算 | 请求拒绝，结算保持待确认 |
| S08 | 以旧版本提交第二次写入 | 返回 `409`，第一次成功结果保留，不覆盖数据 |
| S09 | 业务校验失败后读取空间 | 版本、课时、预约、结算均不应发生部分更新 |
| S10 | 比较各身份返回的数据 | 只有业务所需的品牌、门店、课程、学员、卡片和公告在其范围内 |

## 界面与数据验收

在桌面及窄屏浏览器分别检查四端导航、表单、弹窗、空状态和错误状态。切换角色或门店后，应清除不再适用的选中课程和卡片，避免确认页仍引用上一个门店。提交期间禁用重复按钮，服务端拒绝时显示具体原因并保留可修正的输入。

概览、列表、详情与导出使用一致的数据范围。课时剩余和冻结同时可见；内部结算明确展示待确认与已确认；所有使用示例交易的金额以体验含义命名。学员总数不标为活跃学员，没有订阅合同或真实订单时不宣称真实 MRR、收款或续费率。

构建检查使用项目提供的构建命令；领域检查覆盖预约、取消、签到、完成、跨店确认及权限失败路径。实际执行结果应在交付时报告，未运行的用例不记为通过。

### 本地 Worker 与真实 D1 API 集成验证

2026 年 10 月 24 日，在迁移完成后的构建版 Worker（`npm run start`，`http://127.0.0.1:5173`）执行 `app/tests/api.integration.mjs`，完整流程通过。该测试使用实际本地 D1 绑定，通过 HTTP 请求读写数据，并为测试创建随机私有拥有者空间；不修改浏览器使用的 `local-demo` 数据。

| 检查 | 实测结果 |
| --- | --- |
| 固定角色与读取范围 | 总部仅有本品牌，平台包含 3 个示例品牌；学生仅看本人及绑定孩子，课程容量汇总仍准确 |
| 同一版本两个并发预约请求 | 同时提交 `version=1`，状态恰为 `200`、`409`；最终版本为 `2`，只保留一条有效预约，只增加 1 个冻结课时 |
| 预约、取消及重复消课 | 预约冻结不扣余额；取消释放；未签到消课 `400`；签到后消课成功，重复完成不重复扣课；随后 GET 读取保留结果 |
| 跨店消课与总部确认 | 来访会员消课生成一张 `16800` 分内部清分单；门店确认 `403`，总部确认后保持 `confirmed` |
| 角色越权 | 学生用未绑定会员 `m3` 预约返回 `403`，门店不可确认总部清分 |
| 空间隔离 | 第二个随机认证拥有者的空间仍为版本 `1`、初始余额及初始预约状态，不受首个拥有者操作影响 |
| 品牌暂停 | 平台暂停后，学生业务写入 `403`，存量卡片及已保存余额仍能读取 |
| 请求防护 | 跨来源 Origin `403`；非 JSON Content-Type `415` |
| 非本机来源无认证 | 以非 loopback Host 直接请求本地 Worker、不提供认证头，返回 `401` 和登录提示 |
